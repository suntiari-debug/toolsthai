# การประเมินความครบถ้วนของฟีเจอร์เดิม: Tools Thai

**ขอบเขตการประเมิน:** ฟีเจอร์ที่อยู่ในเวอร์ชันเผยแพร่ล่าสุด `1c7d7251` และรายการที่พัฒนาเสร็จตาม `todo.md` ณ วันที่ 27 สิงหาคม 2569  
**คำตอบสั้น:** **เพียงพอสำหรับ MVP ของผู้ประกอบการรายเดียวที่ออกเอกสารและติดตามเงินรับแบบ manual ได้จริง** แต่ยังไม่ควรถือว่าเป็นระบบเอกสาร/บัญชีที่ครบวงจรสำหรับทีมงานหรือการทำงานที่ต้องเชื่อมระบบบัญชีภายนอก

> Tools Thai มีวงจรหลัก “ออกเอกสาร → ติดตามลูกหนี้ → รับชำระ → ตรวจยอดคงค้าง → ส่งออกข้อมูล” ครบแล้ว ส่วนที่ควรลงทุนต่อคือการปิดวงจรด้วยใบเสร็จอัตโนมัติและลดงานติดตามด้วยการเตือน

## 1. ฟีเจอร์ที่พร้อมใช้งานแล้ว

| กลุ่มงาน | ความสามารถที่มี | ความพร้อมใช้งาน |
|---|---|---|
| เอกสารธุรกิจ | สร้างใบเสนอราคา ใบแจ้งหนี้ ใบเสร็จ ใบส่งของ และใบกำกับภาษี; แปลงใบเสนอราคาเป็นใบแจ้งหนี้โดยคงลูกค้า/รายการสินค้า | พร้อมใช้สำหรับงานเอกสารรายวัน |
| คลังเอกสาร | ค้นหา กรองตามประเภท/สถานะ เปลี่ยนสถานะ ทำสำเนา เก็บถาวร กู้คืน และกลับไปแก้ไขเอกสาร | พร้อมใช้สำหรับการจัดการเอกสารของผู้ใช้คนเดียว |
| PDF | Preview ก่อนส่งออก, เลือกและทำความสะอาดชื่อไฟล์, loading แบบบอกขั้นตอน, export history แบบ owner-scoped | พร้อมใช้และลดความคลุมเครือขณะดาวน์โหลด |
| ลูกหนี้ | เปลี่ยน invoice เป็นลูกหนี้, รับชำระบางส่วน, คำนวณยอดคงเหลือ/สถานะ, ค้นหาและกรองช่วงวันครบกำหนด | พร้อมใช้สำหรับติดตาม AR แบบ manual |
| ความถูกต้องของ payment | แก้ไขผ่าน replacement, ยกเลิกแบบ soft void, บันทึกเหตุผลและ timeline โดยไม่ลบข้อมูลการเงินเดิม | พร้อมใช้ในระดับ audit trail ภายในระบบ |
| รายงานการเงิน | Aging report 5 ช่วงอายุ, ยอดรับชำระตามเดือน/ช่องทาง, export CSV ภาษาไทย โดยไม่นับ payment ที่ voided | พร้อมใช้สำหรับติดตามเงินรับและทวงถามเบื้องต้น |
| ความปลอดภัยข้อมูล | tRPC protected procedures และ owner scope ในเอกสาร ลูกหนี้ payment timeline และ report | พร้อมใช้สำหรับแยกข้อมูลระดับผู้ใช้ |

จากขอบเขตข้างต้น ระบบไม่ใช่เพียง prototype ของหน้าเอกสารแล้ว ผู้ใช้สามารถทำงานต่อเนื่องตั้งแต่ quotation ถึงการติดตามยอดชำระได้ โดยเฉพาะกรณีธุรกิจที่มีผู้ใช้งานหลักคนเดียวและบันทึกข้อมูลด้วยตนเอง

## 2. ช่องว่างที่ยังมีอยู่

| ลำดับ | ช่องว่าง | ผลกระทบธุรกิจ | สถานะปัจจุบัน | คำแนะนำ |
|---:|---|---|---|---|
| P0 | ออกใบเสร็จจาก payment ที่ชำระครบ | ผู้ใช้ยังต้องสร้างใบเสร็จและกรอกข้อมูลจาก invoice เอง | **ออกแบบ UI/UX แล้ว แต่ยังไม่พัฒนา** | ทำเป็นฟีเจอร์ถัดไปทันที |
| P0 | แจ้งเตือนก่อน/หลังครบกำหนดชำระ | การทวงเงินยังต้องเปิด dashboard มาตรวจเอง | ยังไม่มี notification หรือ schedule | เพิ่ม reminder แบบ opt-in หลัง receipt flow |
| P1 | ฐานข้อมูลลูกค้า | ลูกค้าซ้ำยังต้องกรอกข้อมูลในเอกสารใหม่ | มีข้อมูลลูกค้าในเอกสาร แต่ไม่มี customer master | เพิ่มลูกค้า/ที่อยู่/เลขภาษี/ประวัติเอกสารแบบ owner-scoped |
| P1 | หลักฐานรับชำระและกระทบยอด | payment อ้างอิงข้อความได้ แต่ยังแนบสลิปหรือเทียบ statement ไม่ได้ | ไม่มี attachment/bank import | เพิ่มแนบสลิป S3 ก่อนพิจารณา bank import |
| P1 | Version history ของเอกสาร | ทราบ export history แต่ยังไม่เห็นการแก้ไขแต่ละรุ่นของเอกสาร | ไม่มี document revision audit | เพิ่ม revision snapshot และผู้แก้ไข |
| P1 | การส่งเอกสารถึงลูกค้า | ผู้ใช้ต้องดาวน์โหลด PDF แล้วส่งเอง | ไม่มี email/share link | เพิ่ม share link ที่หมดอายุ หรือ email delivery หลังตั้งค่าโดเมนส่งเมล |
| P2 | ผู้ใช้หลายคนและสิทธิ์ตามบทบาท | มี auth พื้นฐาน แต่ไม่ใช่ workspace/team model | ยังไม่มีองค์กร สมาชิก และ permission รายงาน/เอกสาร | ทำเมื่อมีการใช้งานเป็นทีมจริง |
| P2 | เอกสารการเงินเฉพาะทาง | งานภาษี/ปรับปรุงเอกสารต้องทำภายนอกระบบ | ยังไม่มีหัก ณ ที่จ่าย, credit/debit note, e-Tax หรือเชื่อมบัญชี | แยกเป็น roadmap ด้าน compliance และตรวจข้อกำหนดที่เกี่ยวข้องก่อนลงมือ |
| P2 | ภาพรวมการเงิน | มี AR aging แต่ยังไม่ใช่ cash flow, sales trend หรือ P&L | ยังไม่มี dashboard เชิงบริหาร | เริ่มจากยอดขาย/รับชำระรายเดือนก่อนเชื่อมข้อมูลค่าใช้จ่าย |
| P2 | ความพร้อมเชิงปฏิบัติการ | มี checkpoint แต่ควรมีแนวทางกู้คืน/monitoring ที่ทวนสอบได้ | ยังไม่มี alert/backup runbook ในผลิตภัณฑ์ | จัดทำ backup, restore drill และ error monitoring ก่อนขยายผู้ใช้ |

## 3. สิ่งที่ “ไม่ขาด” สำหรับ MVP ปัจจุบัน

ไม่จำเป็นต้องเพิ่ม payment gateway, ระบบสต็อก, POS, หรือ accounting ERP เต็มรูปแบบในรอบถัดไป ฟีเจอร์เหล่านี้เพิ่มความซับซ้อนสูงและไม่ได้แก้ friction หลักของผู้ใช้ใน workflow ที่มีอยู่ การลงทุนก่อนควรเน้นให้ invoice ที่ชำระครบแปลงเป็น receipt ได้อย่างถูกต้อง และช่วยให้ผู้ใช้ไม่ลืมตามหนี้ที่ใกล้ครบกำหนด

## 4. ลำดับพัฒนาที่เสนอ

| ช่วงเวลา | ฟีเจอร์ | เหตุผล | Definition of Done |
|---|---|---|---|
| สัปดาห์นี้ | ใบเสร็จจากรายการที่ชำระครบ | ปิดวงจร invoice-to-cash ลดการคีย์ซ้ำทันที | Receipt draft สร้างจาก paid receivable, ป้องกันซ้ำ, คง source/audit metadata, ผ่าน desktop/mobile QA |
| สัปดาห์ถัดไป | Reminder วันครบกำหนด | ใช้ aging report ที่มีอยู่ให้เกิด action | Opt-in reminders, audit log การแจ้ง, ทดสอบ timezone/duplicate schedule |
| ระยะถัดไป | Customer master + แนบสลิป | ลดงานซ้ำและเพิ่มหลักฐานให้ผู้ตรวจสอบ | CRUD owner-scoped, customer autocomplete, S3 attachment metadata และ permission checks |
| เมื่อเริ่มมีทีม | Workspace roles + revision history | รองรับการมอบหมายงานและตรวจการแก้ไข | Organization boundary, roles, immutable audit records, team QA |

## 5. ข้อสรุปเชิงการตัดสินใจ

หากเป้าหมายคือให้ Tools Thai เป็นเครื่องมือใช้งานจริงสำหรับธุรกิจขนาดเล็กในวันนี้ ฟีเจอร์เดิม **มีเพียงพอที่จะเปิดให้ผู้ใช้ทำงานเอกสารและติดตามลูกหนี้ได้** การเพิ่มฟีเจอร์กว้าง ๆ อื่นก่อนจะทำให้ roadmap กระจัดกระจายเกินจำเป็น

อย่างไรก็ตาม หากต้องการลดงานมือและทำให้ระบบพร้อมกับวงจรรับเงินที่สมบูรณ์ขึ้น ควรอนุมัติฟีเจอร์ **ออกใบเสร็จจากรายการชำระครบ** ตามแบบ UI/UX ที่จัดทำแล้วเป็นอันดับแรก แล้วจึงเพิ่ม reminder การทวงชำระเป็นอันดับถัดไป การทำสองส่วนนี้ต่อเนื่องกันจะใช้ข้อมูลลูกหนี้และ audit trail ที่มีอยู่แล้วได้มากที่สุด โดยไม่ต้องขยายโมเดลข้อมูลเกินความจำเป็น

### ข้อควรระวังด้านขอบเขต

การมีแบบฟอร์มใบกำกับภาษีไม่ได้ยืนยันว่า Tools Thai เป็นระบบ e-Tax Invoice, ระบบยื่นภาษี หรือระบบบัญชีที่สอดคล้องกับกรณีธุรกิจทุกรูปแบบ การเพิ่มฟีเจอร์ภาษีหรือการเชื่อม ERP ต้องกำหนดข้อกำหนดทางธุรกิจและตรวจสอบข้อบังคับที่เกี่ยวข้องเป็นโครงการเฉพาะต่างหาก
